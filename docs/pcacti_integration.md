# P-CACTI Integration

This repository uses P-CACTI for modern-node SRAM modeling and keeps the
patched legacy HP CACTI flow for older nodes. The goal is one generator flow
with a stable `Memory` data contract, regardless of which backend produced the
area, timing, and power numbers.

## Backend Selection

The default backend mode is `auto`:

- `tech_nm < 22` uses P-CACTI.
- `tech_nm >= 22` uses legacy CACTI.

This split is intentional. The checked-in P-CACTI package includes
characterized device XMLs for 7, 14, and 22 nm, while the patched legacy CACTI
path preserves the existing 22 nm and larger coverage.

You can force a backend when debugging or comparing models:

```sh
./scripts/run.py example_cfgs/pcacti7.cfg --model_backend pcacti
./scripts/run.py example_cfgs/freepdk45.cfg --model_backend cacti
```

## Building The Tools

Run:

```sh
make tools
```

This builds the vendored P-CACTI source from `tools/pcacti` and prepares the
legacy CACTI checkout under `tools/cacti`. The P-CACTI source is tracked in git;
its build outputs are ignored. The legacy CACTI checkout is generated by the
makefile and is not tracked.

For P-CACTI-only rebuilds:

```sh
make pcacti_tools
```

## P-CACTI Profiles

P-CACTI-backed configs must use an exact characterized voltage point:

| Node | Device XML | Supported voltages |
| --- | --- | --- |
| 7 nm | `xmls/devices/finfet_7nm_std.xml` | `0.45 V` super-threshold, `0.3 V` near-threshold |
| 14 nm | `xmls/devices/cmos_14nm_std.xml` | `0.8 V` super-threshold, `0.55 V` near-threshold |
| 22 nm | `xmls/devices/cmos_22nm_hp.xml` | `0.8 V` super-threshold |

Auto mode routes 22 nm to legacy CACTI for contiguous legacy coverage. Forced
P-CACTI at 22 nm is available for comparison if the config uses the supported
0.8 V point.

Unsupported P-CACTI voltages fail before invoking the tool, so Liberty voltage
metadata cannot silently drift from the modeled device point.

## Runtime Artifacts

For each P-CACTI-backed SRAM, the result directory contains:

- `pcacti.xml`: generated P-CACTI cache config.
- `pcacti_sram_cell.xml`: generated SRAM cell config referenced by `pcacti.xml`.
- `pcacti_detailed_report.txt`: captured P-CACTI stdout.
- `pcacti_report.txt`: compact human-readable P-CACTI summary.
- `pcacti.csv`: machine-readable fields consumed by `Memory`.

The CSV uses the same field contract as the legacy CACTI path:

```text
tech_node_nm,capacity_bytes,associativity,output_width_bits,
access_time_ns,cycle_time_ns,dyn_read_energy_nj,dyn_write_energy_nj,
standby_leakage_per_bank_mw,area_mm2,fo4_ps,width_um,height_um
```

`Memory` then feeds those fields into LEF, Liberty, Verilog, memlib, and
techmap generation. The P-CACTI width/height output is normalized to match the
legacy CACTI contract.

## Modeling Notes

The generated macro shape still comes from the requested `port_shape`. P-CACTI
only receives the modeling view needed to produce PPA.

Important compatibility rules:

- Narrow memories are modeled with an 8-byte minimum P-CACTI block size while
  preserving the actual macro bus width.
- Write-only SRAMs are modeled with one surrogate read-write port because
  P-CACTI always computes read energy. The generated macro remains write-only.
- Banks must be a positive power of two.
- Missing P-CACTI device XMLs and unsupported process nodes fail early with
  explicit errors.

## Example

The checked-in 7 nm example uses the P-CACTI flow:

```sh
make tools
make run CONFIG=example_cfgs/pcacti7.cfg
```

That example includes 1RW, 1RW1R, and write-only shapes so the P-CACTI path
exercises the important port mappings.
